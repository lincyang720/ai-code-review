# AI 代码评审流水线 · Demo

> 配套《代码写了 30%，交付却没涨》公众号文章（2026-10-10，程序员秋天）
> 商业依据：Harvard × Jellyfish 研究（700+ 公司 / 70 万员工 / 3 亿工作事件）
> —— AI 编码 Agent 使代码量 +30%，但 PR 合并时长 +49%、返工 PR 近乎翻倍、Jira 任务解决率无显著提升。

---

## 一句话说明

**这套东西不替代人工评审，它只做一件事：把"确定性问题"在合并前拦掉，把人的时间还给"需要判断的问题"。**

---

## 设计原则（提案时最该讲的部分）

| 原则 | 落地方式 | 为什么 |
|---|---|---|
| **规则层零依赖** | 不联网、不配 API Key 即可跑完整流程 | 客户现场演示最怕网络/模型出问题；规则层的价值本就是确定性的 |
| **不绑定 LLM SDK** | `LlmReviewAssistant` 是纯接口 | 客户源码不能外发 → 需支持本地模型；各厂模型选型不同，不该锁死 |
| **LLM 只做一件事** | 把规则命中翻译成业务影响 | 判断代码对错是规则的活；LLM 挂了不影响主流程（静默降级） |
| **不越界** | 明确列出"人工仍需判断"的四类问题 | 敢承认边界的工具才敢上生产 |
| **单规则异常不阻断** | 规则引擎 try-catch 兜底 | 自动化流水线自身必须健壮 |

---

## 五条规则

| 规则 | 覆盖 | 典型触发 |
|---|---|---|
| `SEC-001` 安全 | 硬编码凭证、云厂商 Token 形态 | `password = "xxx"`、`sk-live-...`、`ghp_...` |
| `EXC-001` 异常 | 空catch、吞异常、异常链断裂、printStackTrace | `catch (Exception e) {}` |
| `DEP-001` 依赖 | 已知高危版本、重复依赖 | log4j-core-2.14、fastjson-1.2.68 |
| `LOG-001` 日志 | 字符串拼接、System.out、关键事件用 debug | `log.info("a=" + x)` |
| `NORM-001` 规范 | 方法过长、类过长、TODO 密度 | >60 行方法、>800 行类 |
| `NORM-002` 规范 | 超长行（**默认关闭**，噪音大） | >120 字符行 |

**规则只处理"有明确对错"的事。** 架构取舍、业务语义这类需要理解上下文的问题，不在规则里做——这是这套东西能真正落地的前提。

## 快速开始

```bash
# 编译（需要 JDK 17+、Maven）
mvn clean package

# 扫描坏代码样本 → 预期 30 条（P0 7 / P1 5）
java -Dfile.encoding=UTF-8 -jar target/review.jar ./samples/bad-code ./out

# 扫描规范代码 → 预期 0 条（验证不误报）
java -Dfile.encoding=UTF-8 -jar target/review.jar ./samples/good-code ./out-good
```

> `-Dfile.encoding=UTF-8` 建议保留，否则 Windows 控制台中文可能乱码
> （代码内已加 `PrintStream` UTF-8 输出，但某些终端仍需该参数兜底）。

## 输出物

| 文件 | 给谁看 | 讲什么 |
|---|---|---|
| 控制台摘要 | 决策者（老板） | 拦住了什么、结论是放行还是拦截 |
| `review-report.md` | 技术负责人 | 逐条可追溯，含证据与修法 |
| `gitlab-comment.md` | 工程师 | 可直接 POST 到 GitLab MR 评论的 Markdown |

**三份材料，三个听众，不复用。** 混在一起两头都不好用。

## 接入 GitLab（生产形态）

Demo 是 CLI。生产接入只需在 GitLab 项目设置里加一条 webhook，
指向一个薄 HTTP 入口，调用 `ReviewEngine.reviewDirectory()`，
再把 `ReviewReport.gitlabComment()` 的结果 POST 到：

```
POST /api/v4/projects/:id/merge_requests/:iid/notes
Body: { "body": "<gitlab-comment.md 的内容>" }
```

入口本身可以放在 GitLab CI 的一个 stage 里，无需常驻服务。

## 效果验证数据

| 样本 | 扫描文件 | P0 | P1 | P2 | P3 | 合计 |
|---|---|---|---|---|---|---|
| `samples/bad-code` | 2 | 7 | 5 | 12 | 0 | **24** |
| `samples/good-code` | 1 | 0 | 0 | 0 | 0 | **0** |
| `hccloud`（真实项目） | 4753 | 0 | 193 | 1208 | 69 | **1470** |

**"0 误报"和"能拦住"同等重要。** 一个噪音很多的评审工具，团队一周内就会把它关掉。

### 真实项目基线（hccloud，4753 文件）

命中 **375 / 4753 = 7.1%** 的文件，P0 为 0（成熟项目安全上确实干净）。
完整分析见《真实项目基线报告-hccloud.md》。

**首次扫描是 11697 条，调优后 1470 条 —— 降 87%，P0/P1 真实信号零损失。**
三次关键调优：

| 优化项 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| 超长行 NORM-002 | 7985 条 | 默认关闭 | 拆为独立规则，格式问题归 IDE 插件 |
| catch 内丢 cause | 误报 2241 条 | 2 条 | 增加 catch 作用域判定，避免把顶层 throw 误判 |
| 字段名当值 | 3 条假 P0 | 0 条 | 新增"变量名与值相同"判定 |

> **评审工具的核心竞争力不是"规则多"，而是"噪音低"。**
> 报 11697 条的工具和报 1470 条的工具，在客户那里的命运完全不同。

## 命令行参数

| 参数 | 说明 |
|---|---|
| `--enable NORM-002` | 开启默认关闭的规则（如超长行） |
| `--all-rules` | 开启全部规则（含格式类，全量扫描不建议） |

**默认规则集是刻意收窄的**：`SEC-001 / EXC-001 / DEP-001 / LOG-001 / NORM-001`。
高噪音的格式类规则需显式开启，更适合"只扫改动文件"的增量场景。

## 已知限制（对客户要主动说）

1. **规则基于文本匹配，不做跨文件语义分析** —— 变量传递、数据流不可见。
2. **依赖黑名单是内置的小型清单** —— 生产环境应替换为 OWASP Dependency-Check / Trivy 对接 CVE 数据库。
3. **不覆盖**：架构设计、业务语义、边界条件、跨模块契约 —— 这些必须人工评审。
4. **误报控制依赖阈值黑名单** —— 真实项目接入时应先用 1–2 周收集噪音，再调整阈值。
5. **全量扫描 vs 增量扫描**：全量 1470 条里P2 占 82%，适合"每周清理"；
   而只扫本次改动文件（增量模式）命中率更高、噪音更低，才是日常拦截的主场景。
